# 그래프 사용자 개입 기능 — 사전 판단

작성일: 2026-11-13. 대상: 객체 생성·삭제, 사용자 정의 객체 속성·관계 추가.
상태: **설계 검토안. 이번 요청에서는 런타임 코드·DB를 변경하지 않는다.**

## 1. 판단

**도입을 권고한다. 현재 수동 편집을 확장하되, 사용자 수정이 재추출·사양 동기화 뒤에도 보존되는 구조를 먼저 만든다.**

사용자 개입이 전혀 없는 상태는 아니다. 현재는 이름 변경·병합과 정해진 관계의 추가·수정·삭제가 가능하다. 사용자가 원하는 확장은 객체의 독립 생성·삭제/복구, 속성의 정의·값 입력, 새로운 관계 종류의 등록이다. 선택 목록과 입력창만 추가하면 완료되는 작업은 아니다.

제품 사양의 원본은 기존 사양 DB로 유지한다. 그래프 화면에서도 사양 수정과 연결 관리를 할 수 있게 하되 저장은 사양 저장소를 거치게 한다. 별도 그래프 값이 같은 제품 사양을 덮어쓰는 구조는 피한다.

## 3. 선행 해결이 필요한 이유

### 3-1. 수동 객체가 자동 정리에서 사라질 수 있다

현재 객체에는 생성 출처나 수동 보존 상태가 없다. 문서 등장·관계·사양 ref가 없는 객체는 `_prune_orphans`가 지운다. 독립 객체 생성만 추가하면 이후 정리 과정에서 삭제될 수 있다. 사용자가 속성만 입력한 객체도 보호해야 한다. [정리 코드](/C:/TG_AI_DEV/rag_QA/repository/graph_repository.py:853)

### 3-2. 관계 row ID를 장기 식별자로 가정하면 안 된다

문서 재추출은 extract 관계를 교체하고, `seed_specs`는 spec 관계를 삭제 후 다시 넣는다. 기존 관계 수정·방향 전환도 새 행을 만든다. 자동 관계의 row ID에 사용자 메모·속성을 바로 매달면 유실될 수 있다. 1차 범위에서는 임의 속성을 객체에 우선 제공하고, 수동 관계는 삭제 대신 상태·이력을 보존한다. 자동 관계의 임의 속성 확장은 별도 안정적 관계 식별 설계 후 제공한다. [문서 교체](/C:/TG_AI_DEV/rag_QA/repository/graph_repository.py:177), [사양 동기화](/C:/TG_AI_DEV/rag_QA/repository/graph_repository.py:97)

### 3-3. 수동 관계도 근거 파일 삭제와 함께 지워지는 경로가 있다

`graph_relation.file_id`는 파일 삭제에 연쇄 삭제된다. 현재 테스트도 근거 파일이 삭제되면 그 파일에 묶인 manual 관계가 사라지는 것을 기대한다. 사용자 입력을 보존하려면 수동 사실과 파일 참조를 분리하고, 파일이 없어져도 입력·출처 스냅샷과 변경 이력을 남겨야 한다. [기존 테스트](/C:/TG_AI_DEV/rag_QA/tests/test_graph_edit.py:100)

### 3-4. 그래프 편집과 사양 DB 편집의 의미가 다르다

사양 DB의 parent_id·product_component가 그래프의 variant_of·has_component로 투영된다. 그래프에 같은 관계를 수동으로 추가해도 사양 DB를 수정하는 것은 아니다. 이후 `compare_specs`와 그래프가 서로 다른 정보를 보일 수 있다.

따라서 연결된 제품의 구성·상위 모델 변경은 사양 서비스에 저장하고, 화면에만 보이지 않게 하는 조작은 그래프의 제외 상태로 저장한다. 두 동작의 버튼·영향 안내를 분리한다. [현재 사양 변경 후 동기화](/C:/TG_AI_DEV/rag_QA/app/routers/specs.py:37)

### 3-5. 고정 종류가 서버·추출기·화면에 흩어져 있다

API 허용 목록, LLM 구조화 출력의 Literal, 화면의 관계 라벨·선택 목록이 모두 고정이다. 새 관계를 DB에만 넣으면 화면의 `RELATION_META[edge.type].label` 접근에서 실패할 수 있다. 수동 편집용 동적 스키마와 LLM 자동 추출용 허용 스키마를 구분해야 한다. [화면 표시](/C:/TG_AI_DEV/rag_QA/frontend/src/knowledge/GraphCanvas.tsx:303)

## 4. 권장 사용자 경험

1. **객체 추가:** 관계 없이 먼저 만들고 이름·별칭·속성을 입력한다. 사양 DB의 제품·부품을 연결할 수도 있다.
2. **속성 추가:** 속성명·자료형·단위/선택지를 등록하고 대상 객체에 값을 입력한다. 제품 사양 용도이면 기존 사양 DB 속성·값으로 등록한다.
3. **관계 추가:** 기존 관계를 고르거나 새 관계 이름·방향·연결 가능한 객체 종류를 등록한다.
4. **객체 삭제:** 영향받는 연결·속성·사양 연결을 미리 보고 그래프에서 제외한다. 이후 복구할 수 있다.
5. **출처 확인:** 문서 추출·사양 DB·사용자 입력을 구분하고 누가 무엇을 바꿨는지 본다.

예: `A650 → 대체 후보 → B모델`을 사용자가 추가하고 사유를 남길 수 있다. 이 관계가 생겼다는 것만으로 사양 충족이나 입찰 적합을 확정하지 않는다. 실제 충족 여부는 조건·구성·근거를 함께 판정한다.

## 5. 1차 범위와 후속 범위

**1차 필수:** 독립 객체 생성, 객체 제외·복구, 사용자 정의 객체 속성·관계 종류, 수동 입력 보존, 출처·변경 이력, 사양 수정 경로 구분, RAG 읽기 반영.

기존 객체 종류 7종은 1차에 유지한다. 사용자가 원하는 "속성"은 객체의 항목·값, "관계 추가"는 새 관계 종류 등록까지 포함하는 것으로 해석했다. 객체 분류 자체의 추가가 필요하면 2차에 종류 레지스트리로 확장한다.

**후속 선택:** 사용자 정의 객체 종류, 자동 관계의 임의 속성, 대량 편집, AI의 사용자 정의 종류 추출 제안. AI가 사용자 schema를 임의로 만들거나 수정한 사실을 자동 승인하는 기능은 포함하지 않는다.
