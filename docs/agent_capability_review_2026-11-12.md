# rag_QA 에이전트 역량 진단 및 메일 멀티턴 설계 검증

검토일: 2026-11-12, Asia/Seoul. 기준 커밋: `1967bc8` 및 현재 작업 디렉터리.

## 1. 판정과 검증 범위

전달된 7개 문제의 핵심은 모두 코드에서 확인된다. 메일 업무를 중심에 놓고 근거 정합성 → 사양·탐색 도구 → 지속적인 대화로 발전시키는 방향은 타당하다. 다만 다음 세 가지는 수정해야 한다.

1. 현재 시스템은 **요청 간 상태를 보존하지 않는 RAG 에이전트**다. `create_agent`는 한 요청 안에서 모델과 도구를 반복 실행할 수 있으므로, “5개 도구를 각각 한 번 호출하는 고정 파이프라인”이라는 설명은 부정확하다. `agent.invoke()` 한 번과 LLM 호출 한 번은 다르다.
2. Checkpointer 추가는 대화 상태 저장에 필요한 기반이다. 검색 품질, 사양 비교의 정확성, 문서 버전 관리, 검증 강제, 중복 발송 방지는 별도로 구현해야 한다.
3. `task_id = thread_id`는 해당 메일의 내부 반려·재작성에는 적합하다. 고객 회신까지 이어가려면 메일 대화의 `conversation_id`와 개별 검토 작업의 `task_id`를 분리하는 편이 적합하다.

검증은 소스 읽기, 로컬 SQLite 읽기 전용 조회, 실제 함수의 AST를 격리 실행한 13개 사례로 수행했다. SMTP·파서·LLM은 대역을 사용했고, 운영 애플리케이션을 import하지 않았다. 실제 메일 발송·LLM 호출·배포 서버 확인은 수행하지 않았다. 호출한 Python 3.12 환경에는 LangChain, LangGraph, pytest가 없어 전체 통합 테스트는 실행하지 않았다. 아래 내용은 실제 모델의 정답률 벤치마크가 아니다.

로컬 `storage/mail.db`의 읽기 전용 조회 결과:

| 항목 | 수량 |
| --- | ---: |
| 문서 / 페이지 행 | 1 / 1 |
| 제품 / 부품 / 사양 값 | 4 / 123 / 1,572 |
| 그래프 개체 / 별칭 | 21 / 34 |
| 수신 메일 / 작업 | 127 / 127 |
| 원문과 달라진 검수 페이지 | 0 |
| 페이지 텍스트가 없는 파일 | 0 |

이는 로컬 DB의 상태이며 배포 DB의 상태를 의미하지 않는다. 검수 텍스트 무시 문제는 실제 함수에서 재현했지만, 이 로컬 DB에 이미 수정된 페이지가 있다는 의미는 아니다.

## 2. 전달된 7개 진단 대조

### ① 검수 텍스트를 무시하고 원본 재파싱: 확인, 최우선

- `tools/tool.py:255`의 `_extract_text`는 `parse_file`을 호출한다. `read_source_document`는 이 경로를 사용하며 `file_page.text`를 조회하지 않는다.
- `app/routers/files.py:229`의 검수 저장은 임베딩을 교체하고 `file_page.text`를 수정하며 그래프 재추출도 예약한다. 원본 파일은 바꾸지 않는다.
- 따라서 검색·그래프에서 확인한 텍스트와 최종 읽기 텍스트가 달라질 수 있다. PDF 파서는 이미지 OCR 경로를 포함한다. 다만 재파싱은 경로와 mtime 기반 LRU 캐시의 미적중 때 발생하므로 “모든 질문마다 반드시 OCR”은 아니다.
- `graph_rag/service.py:22`의 그래프 인덱싱은 이미 저장된 페이지 텍스트를 사용한다. 이 경로를 문서 읽기 도구와 통일해야 한다.

권고: 원본 바이너리는 열람·첨부용으로 유지하고, 답변 근거는 `file_id + page_id + revision`으로 식별하는 저장된 페이지 텍스트를 사용한다. 페이지가 없는 과거 파일은 업로드·마이그레이션 단계에서 가져온다. 질문 중 묵시적 OCR로 되돌아가지 않는다. XLSX는 같은 페이지 번호에 여러 행이 있으므로 `page`, `page_id`, `seq`를 구분한다.

### ② 사양 DB와 에이전트 단절: 확인, 높은 사업 효과

- `agent/agent.py:24`의 TOOLS에는 사양 조회·비교 도구가 없다.
- `repository/spec_repository.py:242`는 제품 자체 사양, 연결 부품, 상위 모델 경로를 반환한다. 부품 상세 사양은 별도 조회가 필요하다.
- **상위 모델 경로 조회가 사양 상속 계산을 의미하지 않는다.** 부모 값과 자식 값의 우선순위, 부품 값의 반영, 기본 구성과 옵션의 의미를 결정하는 로직이 필요하다.
- 사양에는 이미 `source_file_id`, `source_page`, `source_note`가 있어 근거 연결의 기반이 있다. 다만 모든 값에 근거·검수 완료 상태가 있다는 보장은 없다.

권고: 조회 도구뿐 아니라 실효 사양 계산과 규칙 기반 비교 서비스를 만든다. 상속은 도메인에서 허용한 속성에만 적용하고, 알 수 없는 값·구성 미지정·근거 충돌을 별도로 반환한다. LLM에는 모델명·요구 조건 추출과 결과 설명을 맡긴다.

### ③ 그래프 경로의 출처 누락: 확인, 수집·응답 두 계층 수정 필요

- `agent/agent.py:181`의 `_collect_sources`는 검색·리랭크 메시지만 수집한다.
- `run_agent`에도 별도의 수집 구현이 있어 두 경로 모두 수정해야 한다.
- `graph_search` 결과는 문서마다 `pages`를 갖는 사전이고, 원문 읽기는 문자열이다. 이를 검색 결과 목록처럼 단순 추가하면 `page`, `text`를 요구하는 `/ask` 응답과 맞지 않는다.
- 추가로 `app/routers/mails.py:102`는 저장된 근거의 존재와 관계없이 `sources=[]`를 반환한다. 수집만 고쳐서는 메일 검토 화면이 고쳐지지 않는다.
- `tests/test_mail_list.py:128`도 빈 배열을 기대하고 있어, 근거를 저장한 사례를 추가하고 기대 동작을 바꿔야 한다.
- 추가로 `run_agent`는 JSON 문자열 목록을 파싱한 직후 한 번, list 검사에서 다시 한 번 추가한다. 같은 출처가 두 번 들어가는 경로를 재현했다.

권고: 검색 후보와 답변에 사용한 근거를 분리하고, 답변이 지정한 `evidence_ids`를 서버가 해석해 출처를 만든다. 문서·사양·고객 첨부를 하나의 근거 형식으로 통일하고 파일 ID를 보존한다. 파일 ID가 빠지면 참고 문서 첨부 후보 조인도 실패한다.

### ④ 페이지 점프·목록·정확 검색 부재: 확인, 표현 보완

- `read_source_document`는 임의의 글자 오프셋을 받을 수 있으므로 코드가 시작 위치 0만 허용하는 것은 아니다. 다만 프롬프트가 처음부터 순서대로 읽도록 강제하고 페이지 점프는 제공하지 않는다.
- `search_documents`에는 이미 `file_id`, `page` 필터가 있다. 이는 페이지 전체를 직접 읽는 도구를 대신하지 않는다.
- 파일 목록 저장소와 API는 있으나 모델이 호출할 목록·키워드 검색 도구는 없다.

권고: 페이지 직접 읽기, 필터·페이지네이션을 가진 문서 목록, `file_page.text`를 대상으로 한 문자열 검색을 추가한다. 정확 검색은 모델명·인증번호·문서명을 우선 처리하고 의미 검색과 결합한다. FTS를 도입한다면 한국어 토크나이저의 부분 일치 특성을 별도로 검증한다.

### ⑤ 한국어 조사 결합 개체 매칭: 조건부 재현, 확인

- `repository/graph_repository.py:314`는 공백·쉼표 단위로 자른 정규화 토큰을 접두 매칭에 사용한다.
- 별칭에 `N5800 14세대`만 있을 때 `N5800`은 찾고 `N5800의 사양`은 찾지 못한다.
- 짧은 별칭 `N5800`이 이미 등록되어 있거나 질문이 전체 이름을 포함하면 기존 포함 검색으로 성공할 수 있다. 모든 한국어 조사 질문이 실패하는 것은 아니다.

권고: 원문 토큰을 유지하면서 모델 식별자 후보와 조사 제거 후보를 추가한다. `N5800A`, `N5800-GB70-PU02`, 인증번호처럼 경계·접미사가 중요한 표기도 함께 검증한다. 무조건 한글 접미사를 삭제하거나 광범위한 중간 일치로 바꾸지 않는다.

### ⑥ 전문을 LLM이 다시 도구 인자로 복사: 확인, 오류 발생 가능성

- `tools/tool.py:141`, `:173`은 `documents: list[dict]`를 받는다. 서버가 직전 검색·읽기 결과를 참조하는 방식이 아니다.
- LLM의 전문 재출력에 토큰·시간이 들고, 누락·변형 가능성이 있다. 실제 변형 빈도와 지연은 별도 측정해야 한다.
- 고객 첨부는 최초 메시지에 전달된다. “처음부터 첨부가 전달되지 않는다”는 설명은 부정확하다. 다만 `check_answerability`는 전달받은 `documents[*].text`만 확인하며 고객 첨부·이미지 맥락을 자동으로 함께 확인하지 않는다.

권고: 서버가 원문을 보관하는 evidence registry를 만들고 리랭크·검증·인용은 ID를 받는다. 영속 멀티턴에서 쓸 registry는 전역 메모리 사전이 아니라 작업별 접근 범위와 문서 버전을 가진 저장소여야 한다. 이미지 근거는 원본 이미지와 추출·검수 상태를 함께 기록한다.

### ⑦ 프롬프트 충돌·검색 파라미터 무시: 확인

- `agent/prompt.py:18`은 검색부터, `:46`은 모델·인증 질문에서 그래프부터 시작하도록 지시한다. 특정 조건에 대한 예외로 해석할 여지도 있으나 절차가 중복되어 있다.
- 실제 프롬프트는 `prompt_repo.get_system_prompt()`가 선택한 DB 내용이다. 코드의 기본 템플릿만 수정해도 기존 DB 프롬프트가 자동으로 바뀌지는 않는다.
- 로컬 선택 프롬프트는 ID 2이며 `search_documents`, `start=0`, `check_answerability`를 포함한다. 그래프 안내는 실행 시 별도로 덧붙는다.
- `/ask`와 `/ask/attachments`의 두 top-N 파라미터는 실제 검색·리랭크에 전달되지 않는다.

권고: 제품·수치 질문은 사양 도구, 인증·연관 문서는 그래프, 일반 내용은 문서 검색으로 안내를 통일한다. top-N·시간·도구 호출 한도는 프롬프트 부탁이 아니라 서버 실행 설정으로 적용하고 로그에 남긴다. DB 프롬프트 변경은 버전과 명시적 적용 절차를 둔다.

## 3. 추가로 확인한 운영상 우선 과제

| 과제 | 코드 근거와 영향 | 권고 |
| --- | --- | --- |
| 근거 확인을 강제하지 않음 | `_invoke_logged`는 마지막 답변을 그대로 반환. `check_answerability` 생략·실패 결과를 차단하는 코드가 없음 | 답변 구조 검증과 근거 확인을 명시적 노드로 만들고 통과한 초안만 저장 |
| 검증 범위가 부족함 | `check_answerability`는 답변 가능성을 판단하며, 실제 생성된 답변의 개별 주장과 수치를 검증하지 않음 | 답변 생성 후 주장·수치·근거 연결을 검사. LLM 검사는 보조 신호로 사용 |
| 중복 발송 경쟁 | `TaskRepository.approve`는 SELECT만 수행. 라우터는 SMTP 이후에 sent로 변경 | 상태·초안 버전에 대한 조건부 갱신과 유일한 outbox 항목으로 발송 선점 |
| 저장 전 검토 알림 | consumer는 검토 메일을 보낸 후 `save_draft` 실행 | 초안·근거·버전 저장을 먼저 커밋하고 알림을 별도 outbox에서 전송 |
| 작업 선점 없음 | pending 조회 후 처리 중 상태·lease 없이 실행. 프로세스마다 메일 루프 시작 | 단일 worker 또는 원자적 작업 선점, 만료 복구와 같은 대화의 순차 처리 |
| 승인 주체·승인 버전 | 앱 코드에 로그인된 담당자 확인이 없고 요청 IP만 기록. 승인한 초안 버전도 별도 바인딩 없음 | 인증된 담당자 또는 범위를 제한한 일회성 토큰, 초안 해시·버전·첨부 목록과 승인 연결 |
| 모델 경로 고정 | 메일 생성과 답변 가능성 판정은 `local` 고정 | 동일 도구·평가셋으로 모델별 비교 후 정책 결정. 현재 배포 모델 성능은 미측정 |
| 제한·관측 미흡 | 시간·도구별 개수는 로그에 있으나 질문별 품질·비용·검토 성과는 부족. `/mails/stats`는 고정 예시 값 | run별 모델·프롬프트·검색 설정·토큰·지연·근거·반려 원인을 기록 |

외부 프록시·망 접근 제어는 확인하지 않았으므로 앱 인증 부재가 곧 인터넷 공개 취약점을 뜻하지는 않는다. 다만 승인 주체의 식별과 기록은 메일 업무 자체에 필요하다.

SMTP 발송과 DB 커밋은 하나의 트랜잭션으로 묶을 수 없다. outbox를 사용해도 SMTP 수락 직후 장애가 나면 성공 여부가 모호할 수 있다. `send_unknown` 상태와 확인·재처리 정책을 둔다. 고정 Message-ID만으로 수신 측 중복 제거가 보장되지는 않는다.

## 4. 상용 에이전트와의 차이

Codex와 Claude Code는 모델 주위에서 도구 실행·상태·검증·권한을 관리하는 실행 계층, 즉 harness를 제공한다. Claude Code 공식 문서는 맥락 수집 → 행동 → 결과 검증의 반복, 세션 재개와 맥락 압축을 설명한다. Codex 공식 문서는 대화 상태, 실행 이벤트, 도구, sandbox와 승인 정책을 실행 계층의 역할로 설명한다. [Codex 공식 문서](https://developers.openai.com/blog/codex-as-a-platform), [Claude Code 공식 문서](https://code.claude.com/docs/en/how-claude-code-works)

아래 오른쪽 열은 해당 개념을 이 프로젝트에 적용한 설계 권고다. 상용 제품이 사내 사양·인증 업무의 정답을 자동 보장한다는 뜻은 아니다.

| 역량 | 현재 rag_QA | 이 프로젝트가 갖춰야 할 동작 |
| --- | --- | --- |
| 실행 내 반복 | create_agent 기반 도구 반복 가능 | 현재 루프를 유지하되 근거 부족·충돌에 따라 추가 탐색 |
| 탐색 범위 | 의미 검색·개체 그래프·오프셋 읽기 | 목록·정확 검색·페이지 읽기·사양 조회의 조합 |
| 업무 데이터 계산 | 사양 DB에 도달하지 못함 | 단위·옵션·파생 모델을 고려한 코드 기반 비교 |
| 대화 연속성 | 매 실행 새 메시지 | 내부 검토 재개, 승인한 고객 대화 이력 사용 |
| 맥락 관리 | 원문 복사·첨부 재파싱 | 근거 ID·버전, 첨부 저장, 선택적 로딩과 요약 |
| 결과 검증 | 답변 가능성 판단을 프롬프트로 요청 | 생성 후 수치·주장·근거·누락 항목 검증 |
| 행동 제어 | UI 승인 있으나 상태 전이와 식별 약함 | 승인 대상 버전 고정·원자적 발송 선점·감사 이력 |
| 오류 복구 | failed 상태와 수동 대응 중심 | 실행 재개·작업 lease·오류 종류별 재시도·발송 결과 조정 |

도구 개수가 적거나 도구 목록이 고정이라는 사실 자체는 결함이 아니다. 필요한 업무를 수행하는 도구의 계약과 실행 제어가 핵심이다. 범용 셸·자율 발송·여러 에이전트는 지금 단계의 선결 조건이 아니다. 더 강한 모델도 접근할 수 없는 사양 DB나 버려지는 검수 텍스트를 대신 연결해 주지 못한다.

## 5. 권장 구조

### 고객 대화와 내부 검토의 분리

| 식별자 | 의미 | 예시 |
| --- | --- | --- |
| conversation_id | 고객의 실제 메일 대화 | 최초 질문, 승인 발송 답변, 고객 후속 질문 |
| task_id | 수신 메일 한 건의 내부 검토 작업 | 초안 작성, 반려, 수정, 승인 |
| draft_revision | 검토·승인하는 초안 버전 | v1, v2, v3 |
| run_id | 모델 실행·재시도 한 번 | 지연·토큰·실패·도구 이력 추적 |

초기에는 내부 agent checkpoint를 `task:{task_id}`로 두고 반려를 같은 thread의 다음 턴으로 전달한다. 고객이 회신하면 같은 conversation에 새 task를 만들고, 승인·발송된 이력과 접근 가능한 첨부·근거를 새 작업의 맥락으로 불러온다. 내부 반려 문구와 폐기된 초안을 고객의 확정 대화 이력에 섞지 않는다. 고객 대화 자체를 별도 checkpointer thread로 관리하는 방법도 가능하지만 공개 이력과 내부 상태의 경계는 유지한다.

기존에는 DB에 반려 이력과 직전 초안이 보존되어 다음 실행에 전달된다. 따라서 “아무 기억도 없다”보다는 “문서 도구 이력과 모델 실행 상태를 이어받지 못한다”가 정확하다.

Checkpointer는 메시지와 명시적으로 저장한 상태를 보존한다. 파일, 도구 캐시, 외부 객체의 수명까지 자동으로 보존하지 않는다. 문서를 다시 읽지 않는 효과도 자동 보장이 아니므로 evidence 재사용 정책과 프롬프트를 함께 설계한다. 새 턴에는 새 메시지만 추가하고, 재시도 시 동일 event/review ID로 중복 삽입을 막는다. 같은 thread에 대한 실행은 순차 처리한다.

`langgraph-checkpoint-sqlite`는 별도 의존성이다. 소규모 단일 프로세스 도입은 SqliteSaver로 시작할 수 있다. 애플리케이션 lifespan에 연결 수명을 맞추고 현재 동기 호출·worker thread 사용 방식을 검토한다. 다중 인스턴스·부하 증가 시에는 PostgreSQL과 작업 큐를 검토한다. [LangGraph 상태 저장](https://docs.langchain.com/oss/python/langgraph/persistence), [Checkpointer 구현체](https://docs.langchain.com/oss/python/langgraph/checkpointers)

### 메일 스레딩과 본문 처리

1. 수신·발신 양쪽에 Message-ID, In-Reply-To, References를 저장한다. 발신 메일도 conversation에 매핑해야 고객이 발신 답변에 회신했을 때 연결할 수 있다. POP3 UIDL은 수신함 내 중복 처리용으로 별도 유지한다.
2. In-Reply-To와 References를 우선 조회하되 수신 계정·참여자·접근 범위를 확인한다. 헤더 문자열은 인증 수단이 아니다. 제목의 Re: 또는 같은 제목만으로 자동 병합하지 않는다. 모호하면 새 대화로 두거나 검토 대상으로 표시한다.
3. HTML 구조를 잃기 전에 인용·서명을 식별하고 `raw_body`, `new_body`, `quoted_body`를 보존한다. Outlook·Gmail·한글/영문 전달 구분선·본문 중간 답변을 평가한다. 원문을 보존하며 무조건 첫 구분선 아래를 삭제하지 않는다.
4. 최초 첨부의 파싱 결과·원본·추출 상태를 conversation에서 다시 조회할 수 있게 한다. 파일 해시를 기본 키 자료로 사용하고 파서 버전·교정 버전도 구분한다. 전체 첨부를 매번 프롬프트에 붙이지 않는다.
5. 헤더·본문 정규화·내부 검토 이벤트를 구분해 구조적으로 저장한다. 외부 메일·첨부·검색 문서의 명령문을 내부 검토 지시로 취급하지 않는다.

Message-ID는 메시지 식별, In-Reply-To는 부모 메시지, References는 대화 연결에 사용하는 표준 필드다. [RFC 5322 §3.6.4](https://www.rfc-editor.org/rfc/rfc5322.html#section-3.6.4)

### 업무 흐름과 에이전트의 책임

```text
메일 수신·중복 제거 → 대화 연결·신규 본문 추출 → 작업 선점
  → 근거 탐색·사양 조회를 반복 → 초안 생성 → 근거·수치 검사
  → 초안/근거/버전 저장 → 검토 알림
  → 반려: 같은 내부 작업을 이어서 수정
  → 승인: 승인 버전과 수신자·첨부 확정 → outbox → SMTP → 결과 기록
```

탐색은 모델이 선택하도록 하고, 저장·승인·발송의 상태 전이는 코드가 통제한다. 필요하면 상위 LangGraph workflow의 탐색 노드 안에서 기존 `create_agent`를 재사용한다. 모든 내부 처리를 새 프레임워크로 다시 작성할 필요는 없다.

### 도구와 근거 계약의 제안

제안 API는 현재 구현된 API가 아니다.

| 도구 | 입력의 핵심 | 반환의 핵심 |
| --- | --- | --- |
| list_documents | 이름·그룹·종류 필터, limit, cursor | file_id, 이름, 버전, 페이지 수 |
| grep_documents | 정확 문자열, file_ids, page 범위 | 일치 페이지·스니펫·evidence_id |
| read_source_document | file_id, page/pages, block 범위 | 저장 텍스트·revision·evidence_id·이어읽기 정보 |
| get_product_specs | product_id, 구성 조건 | 직접/허용 상속/부품 값, 기본·옵션 구분, 근거 |
| compare_specs | 제품 ID들, 정규화된 조건 | 충족/미충족/확인 필요, 판정 근거 |
| rerank_documents | question, evidence_ids | 정렬된 evidence_ids |
| validate_draft | draft, claim/evidence 연결 | 근거 누락·충돌·수치 오류·미해결 요구 사항 |

사양 비교 예: “RAM 32GB 이상”은 기본 탑재 16GB, 최대 확장 64GB, 선택 가능한 32GB를 서로 다른 의미로 판정해야 한다. 인증도 제품군의 인증이 특정 파생 모델까지 적용되는지 자동 추론하지 않고 적용 모델의 근거를 확인한다. 문서와 사양 DB가 충돌하면 최신·검수·적용 구성에 대한 명시적 정책으로 결정하고, 해결되지 않은 충돌은 담당자에게 드러낸다.

근거에는 최소 `evidence_id, origin_type, file_id/spec_value_id/attachment_id, page_id, page, revision, text, content_hash`를 둔다. 등록 파일·고객 첨부·수동 사양 값의 nullable 필드와 권한 범위를 명시한다. 검색 결과, 그래프, 요약의 개체 이름만으로 사실을 확정하지 않는다. 장기 대화는 요약하되 숫자·인증번호·근거 원문은 ID와 함께 보존하고, 원문이 바뀌면 재검증한다.

## 6. 권장 구현 순서와 완료 조건

### 1단계: 답변 근거와 메일 신뢰성 복구

- DB 페이지 읽기와 page/pages 직접 접근.
- 검색·그래프·읽기 출처의 공통 스키마와 최종 사용 근거 표시.
- `/ask` 중복 출처와 `/mails/{task_id}` 빈 출처 수정.
- 한국어 모델명 후보 추출과 프롬프트 경로 정리. top-N 설정의 실제 전달.
- 생성 후 근거 검증, 초안·근거 저장 후 알림, 원자적 승인·발송 선점.

완료 조건: 수정한 텍스트가 검색·읽기·검토 화면에서 일치하고, 그래프만 이용해도 올바른 페이지가 보인다. 동시 승인으로 발송 작업이 두 개 생성되지 않는다. 근거가 부족한 초안은 부족 사유가 표시된다.

### 2단계: 사양·탐색 역량과 ID 기반 근거 처리

- 제품·부품 조회, 실효 사양 계산, 비교 서비스.
- 문서 목록과 정확 검색, 검색 실패 시 재탐색.
- ID 기반 리랭크·검증, 첨부 evidence 등록·파싱 결과 재사용.
- 로컬/외부 모델을 같은 질문·도구·근거로 비교 평가.

완료 조건: 파생 모델·기본/옵션·미등록 값·단위가 다른 요구 조건을 구분하고, 판단에 사용한 DB 행과 페이지를 함께 제시한다.

### 3단계: 내부 반려 루프의 영속화

- 전용 checkpoint 저장소, task thread, review/event ID.
- 새 반려 내용만 추가하고 기존 evidence를 버전 확인 후 재사용.
- 초안 수정본을 새 revision으로 저장하고 승인 당시 버전을 고정.
- 재시작 복구, thread 순차 처리, 요약·보존 기간·실행 예산.

완료 조건: 문체 수정만 요청한 반려에서 불필요한 재파싱·전면 재검색이 발생하지 않는다. 서버를 재시작해도 이어서 작업할 수 있으며 반려 이벤트가 중복 적용되지 않는다.

### 4단계: 고객 회신 대화와 운영 확장

- 수신·발신 헤더와 conversation 매핑, 신규 본문 추출.
- 승인 발송 이력과 최초 첨부를 후속 작업이 참조.
- 고객 대화와 내부 검토 이력의 분리, 권한별 조회.
- 작업 lease/outbox 복구, 필요 시 전용 worker·PostgreSQL 전환.

완료 조건: 고객이 “앞서 보낸 사양서에서 SSD만 1TB로 바꾸면?”이라고 회신하면 최초 첨부·승인 답변을 찾아 필요한 부분만 재검토한다. 다른 고객의 같은 제목은 연결되지 않는다.

## 7. 평가 기준

기능 도입 전 실제 업무 사례를 익명화한 기준 평가셋을 만들고 현재 결과를 먼저 기록한다. 임의의 성능 수치나 자동화율을 현재 성과로 제시하지 않는다.

필수 사례: OCR 교정 후 질문, 그래프 단독 경로, 25페이지 직접 읽기, 조사 결합 모델명, 비슷한 모델·인증번호 구분, 부모/자식 사양 충돌, 기본/옵션 혼동, 단위 비교, 사양 누락, 고객 첨부만 있는 질문, 이미지 첨부, 문체 반려, 사실 반려, 재시작 복구, SMTP 성공 여부 불명, 동시 승인, 고객 후속 회신, 인용문 중간 답변, 다른 고객의 같은 제목, 문서 수정 후 과거 근거 재사용, 외부 문서의 지시문.

품질 지표: 요구 조건별 정답률, 주장별 근거 정확도·커버리지, 근거 없는 수치 비율, 적절한 확인 요청/답변 보류, 사양 충돌 노출.

업무 지표: 초안 채택률, 담당자 수정량, 사실 오류로 인한 반려율, 검토 시간, 메일 한 건당 완료 시간.

운영 지표: p50/p95 지연, 모델 입출력 토큰, 도구별 호출 수, 재파싱 횟수, 캐시 적중, 상태 복구 성공률, 중복·미확정 발송 건수. 모델·프롬프트·문서 버전과 함께 기록한다.

| 원본 읽기 함수 실행 | 원본 파서 대역 1회 호출 |
| 교정 텍스트와 다른 원본 파싱 결과 | 원본 오류 문자열 반환, 교정 문자열 미포함 |
| send_email의 SMTP 대역이 받은 메시지 | Message-ID / In-Reply-To / References 모두 없음 |
| SMTP 전송 중 두 번째 승인이 끼어드는 순서 | 발송 대역 2회 호출 |
| 도구 없는 최종 답변을 반환하는 에이전트 대역 | _invoke_logged에서 그대로 반환 |

위 13개는 현재 결함 또는 대조군을 확인한 진단 사례다. 수정 후의 통과 테스트, 실제 LLM의 행동, Outlook 클라이언트의 실제 스레딩 검증으로 해석하면 안 된다. 운영 소스 코드는 변경하지 않았다.
